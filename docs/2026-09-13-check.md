# 2026-09-13 센서 점검 기록

## 환경

- NVIDIA Jetson Orin Nano Engineering Reference Developer Kit Super
- Jetson Linux R36.4.7 / Linux 5.15.148-tegra / aarch64
- 초기 인계 자료에는 부팅 불가로 적혀 있었지만 실제 로컬 점검 시 부팅되어 있었음.
- 샌드박스 내부에서는 /dev가 제한되어 보임. 호스트 장치 접근으로 SPI·GPIO 존재 확인.

## SPI 설정 전후

설정 전 CH0~CH4 각 10회 읽기에서 모두 0. 사용자 Jetson-IO 조회에서 P19·21·23·24가 unused.
사용자가 Jetson-IO에서 spi1을 설정하고 재부팅함.
이후 활성 디바이스 트리에서 P19·21·23·24·26의 function=spi1 확인.
부팅 DEFAULT는 JetsonIO이며 `/boot/jetson-io-hdr40-user-custom.dtbo`를 사용함.

100kHz와 500kHz에서 각 10회씩, 채널당 총 20회 읽은 범위:

| 채널 | ADC 최소~최대 | 전압 범위 (VREF 3.3V 가정) | 해석 |
|---|---|---|---|
| CH0 | 181~186 | 0.584~0.600V | MQ-4 #1 입력 읽힘 |
| CH1 | 115~121 | 0.371~0.390V | MQ-4 #2 입력 읽힘 |
| CH2 | 2~5 | 0.006~0.016V | 미연결, 센서 측정값 아님 |
| CH3 | 0 | 0V | 미연결, 센서 측정값 아님 |
| CH4 | 820~834 | 2.645~2.690V | 토양수분 입력 읽힘 |

SPI 설정으로 전 채널 0 현상은 해소됨. 가스 ppm·수분 % 변환 및 정확도는 검증하지 않음.

## DHT22

SPI 설정 전후 모두 P15 측정 요청 3회에서 초기 HIGH, 응답 에지 0개.
사용자 공간 폴링/방향 전환 지연으로 응답을 놓칠 가능성도 있음.
사용자 관리자 조회:

```text
pin 85 (SOC_GPIO39_PN1): (MUX UNCLAIMED) (GPIO UNCLAIMED)
pull=1
tristate=1
enable-input=1
open-drain=1
io-reset=1
rcv-sel=1
io-hv=1
schmitt=0
pull-down-strength=0
pull-up-strength=0
drive-type=0
gpio-mode=1
function=rsvd1
```

입력은 활성화되어 있으나 패드 출력이 tristate 상태여서 시작 LOW를 구동하지 못하는 원인 후보.
P15에 function=rsvd1, pull=0, tristate=0, enable-input=1을 추가한 오버레이를 준비함.
외부 10kΩ 풀업을 사용하며 기존 SPI 설정은 보존함.
컴파일 및 실제 기본 DTB에 대한 fdtoverlay 테스트 성공. 하드웨어 효과는 **미검증·미적용**.
부팅 파일 백업 명령을 안내했으나, 저장소 초기화 시 백업 파일은 존재하지 않았음.

## DS18B20

연결되어 있음. `/proc/config.gz`: `# CONFIG_W1 is not set`.
`/sys/bus/w1/devices` 없음. 현재 커널용 1-Wire 코어, w1-gpio, w1-therm 지원과 P7 설정 필요.
오버레이만으로는 현재 없는 커널 드라이버 지원을 대체할 수 없음.

## 기타

microSD 루트 파일시스템에서 기존 오류 이력 2건 및 e2fsck 권고 로그 확인.
현재 센서 문제나 과거 부팅 실패와 인과관계는 미확인. 파일시스템 복구는 수행하지 않음.

## 다음 순서

1. 기존 SPI 오버레이 백업.
2. DHT22 오버레이 적용 후 재부팅, P15 설정 및 ADC·DHT22 재검사.
3. 현재 커널과 일치하는 DS18B20 드라이버 빌드·설정 방법 검토.
4. 응답 확인 후 가스·토양수분 보정 및 실험 데이터 수집 방식 정리.

## DS18B20 외부 모듈 설치 후 재부팅 재점검 (17:23 이후 KST)

사용자: 다른 로컬 Codex 세션에서 드라이버 설치 후 재부팅 완료.

- 커널 버전 5.15.148-tegra 유지.
- 부팅 OVERLAYS는 `/boot/ds18b20-pin7.dtbo` 하나이며 내용은 기존 SPI·P15와 P7·onewire 설정을 포함.
- 활성 DT에서 P19·21·23·24·26 spi1 유지, P15 rsvd1/tristate=0/input=1, P7 rsvd2/tristate=0/input=1 확인.
- 이 세션에서는 부팅·드라이버·P7 설정을 변경하지 않음.

### ADC 재측정

각 채널 100kHz·500kHz 각 10회, 총 20회:

| 채널 | 최소~최대 raw | VREF 3.3V 가정 전압 |
|---|---|---|
| CH0 MQ-4 #1 | 168~173 | 0.542~0.558V |
| CH1 MQ-4 #2 | 109~114 | 0.352~0.368V |
| CH2 미연결 | 1~5 | 측정 대상 제외 |
| CH3 미연결 | 0 | 측정 대상 제외 |
| CH4 토양수분 | 804~809 | 2.594~2.610V |

입력 읽기 유지 확인. 농도·수분 보정의 검증은 아님.

### DHT22 재측정

Python 진단 3회에서 51·63·48개의 에지 검출. 기존 에지 0 상태와 달리 응답 형태의 펄스가 나타남.
40 데이터 비트가 모두 포착되지 않아 체크섬 검증된 온·습도 값은 없음.

GPIO 핸들을 유지하는 C 폴링 진단을 추가해 시도했으나 첫 방식은 8회 중 일부에서만 부분 펄스, 나머지는 0개.
오픈드레인 값 변경으로 전환하는 후속 방식도 8회 모두 펄스 0개. 최종 소스는 `scripts/dht22_probe.c`.
`gcc -O2 -Wall -Wextra -Werror` 빌드는 성공했으나 센서 프레임 수신 검증에는 실패함.
따라서 DHT22 정상 동작 또는 고장 어느 쪽으로도 확정하지 않음. GPIO API 동작·타이밍·신호 확인 필요.

### DS18B20 재점검

- wire·w1_gpio 모듈이 로드됨.
- `/lib/modules/5.15.148-tegra/extra/ds18b20/w1_therm.ko` 설치 확인. vermagic가 현재 커널과 일치하지만 점검 시 로드되지 않음.
- w1_bus_master1 생성됨. 정상 DS18B20 family 0x28 장치가 없음.
- 탐색 ID가 00-800000000000, 00-400000000000에서 00-c00000000000, 00-200000000000, 00-a00000000000 등으로 변함.
- 온도용 `w1_slave`·`temperature` 파일 없음.
- 커널 로그에 `max_slave_count 64 reached`, `Family 0 ... is not registered`, GPIO open-drain 강제 설정 메시지.
- 버스 드라이버가 있다는 것과 온도센서가 정상 인식됐다는 것은 다름. w1_therm 미로드만을 원인으로 단정할 수 없음.
- 다음은 P7 실제 pinconf와 전원·풀업·신호 품질·배선 확인. 다른 세션의 드라이버는 수정하지 않음.

family 0x28 및 CRC/온도 파일 해석 참고: [Linux w1_therm 문서](https://docs.kernel.org/w1/slaves/w1_therm.html).
